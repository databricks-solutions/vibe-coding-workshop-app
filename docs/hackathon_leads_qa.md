# Hackathons in V2V — Q&A for Product/Eng Leads

> **Purpose:** A discussion doc to align with V2V leads on open decisions surfaced by the Hackathons feature. Each item is framed as a question, the current default we shipped, the trade-off, and a recommendation. Bring opinions — these are reversible but cheaper to settle now.

**Status:** Hackathons MVP shipped behind the front-page entry point. Four per-hackathon personas (Organizer, Participant, Judge, Voter), in-memory + Lakebase storage, AI-assisted text generation, searchable judge selector with add-by-email + remove. Plus, this round:

- **Dev persona switcher** (local-only "act as" — gated to `USE_LAKEBASE=false` / `DEV_PERSONA_SWITCH`).
- **Test suites:** 34 API tests (stdlib `unittest` + FastAPI TestClient, no install needed) + 8 Playwright e2e tests covering all persona flows. Both green. The API tests already caught + fixed two real bugs (a `judge-candidates` 500 and an unclamped team-size).
- **Playbook page** under the Hackathons sidebar accordion — persona how-tos illustrated with screenshots + a walkthrough video, both auto-generated by the Playwright suite so the docs never drift from the live app.

The questions below are about how far to take it.

---

## 1. User management & identity  *(the big one)*

**Q: V2V identifies users only by email (from `X-Forwarded-Email` / Databricks SSO). Hackathons introduce real roles (organizer/judge) and a need to *discover* users. Do we want a first-class user/identity model, or keep email-only?**

- **Current default:** Email-only, per-hackathon self-serve roles. The creator is the organizer; judges are added by email; everyone else is a participant/voter. The judge picker sources candidates from `workshop-users` (people who've used the workshop) + invite-by-email.
- **Trade-off:** Email-only is simple, has zero admin overhead, and matches how the rest of V2V works. But there's no global notion of "a user," no profiles/avatars, no way to see "all people in my org," and no invitation lifecycle (a judge is just *added*, they don't *accept*).
- **Recommendation:** Keep email-only for now. Revisit only if we want cross-hackathon identity (profiles, history, "my hackathons" across events). If we do, the cleanest path is a lightweight `users` table keyed by email, populated lazily — not a full RBAC system.
- **Decision needed:** Is email-only acceptable for the foreseeable roadmap, or is a user directory a near-term requirement?

**Q: Should there be a global "admin" who can manage any hackathon, or is per-hackathon ownership enough?**

- **Current default:** No global admin. Only the creator manages their hackathon.
- **Open question:** For workshop facilitators running events, do they need an admin view across all hackathons (moderation, deleting spam, reassigning ownership)?

---

## 2. Judge assignment & invitation lifecycle

**Q: Today, adding a judge is immediate (no acceptance step). HackathonHive had a pending→accepted/declined invitation flow. Do we need invitations?**

- **Current default:** Immediate assignment. Organizer selects/invites by email; that person sees the Judging tab next time they open the hackathon.
- **Trade-off:** Immediate is frictionless for a workshop setting. Invitations add a notification/consent surface (and we have no notification system).
- **Recommendation:** Keep immediate for workshop use. Add invitations only if hackathons go "public" beyond a facilitated workshop.

**Q: Should judges only see submissions assigned to them, or all submissions?**

- **Current default:** All submissions (every judge scores every submission). HackathonHive had `can_view_all_submissions` + per-submission assignment.
- **Open question:** For large hackathons, do we need to shard submissions across judges?

---

## 3. Scoring & results

**Q: Is "average of judge criterion scores, tie-broken by community votes" the right ranking? Should community votes be weighted into the score rather than just a tiebreaker?**

- **Current default:** Rank by avg judge `overall` (mean of 0–10 criteria), tie-break on vote count. Votes are a tiebreaker, not a weighted component.
- **Open question:** Do we want a configurable weighting (e.g. 80% judges / 20% crowd)? A "people's choice" award separate from the overall winner?

**Q: Should results be hidden until the organizer marks the hackathon `completed`?**

- **Current default:** Results (live leaderboard) are visible to everyone at all times.
- **Trade-off:** Live results are engaging but can bias judges/voters. A "reveal" moment is more dramatic.

---

## 4. Teams & submissions

**Q: One submission per team, team leader submits. Right constraints?**

- **Current default:** One submission per team (DB-enforced unique on `team_id`); only the team leader can submit/edit. A user can be on one team per hackathon.
- **Open questions:** Multiple submissions per team? Any team member can edit? Solo participants (team of one) — is the current min-team-size=1 default the right UX, or should solo be a distinct path?

**Q: Team formation — do we need join requests / approvals, or is open-join enough?**

- **Current default:** Open join (anyone can join any non-full public team). HackathonHive had join-request → leader-approval.
- **Recommendation:** Open-join for workshops; approvals add friction we probably don't want.

---

## 5. AI assistance

**Q: We added "Draft with AI" on descriptions, taglines, team bios, submission summaries, and judge feedback (Databricks Model Serving, Claude). Any concerns about AI-drafted *judge feedback* specifically?**

- **Current default:** Judges can AI-draft feedback from their scores + notes.
- **Open question:** Is AI-drafted judge feedback appropriate (efficiency) or does it undermine the authenticity of judging? Should it be labeled as AI-assisted?

---

## 6. Persistence, scale & lifecycle

**Q: Hackathon data uses new Lakebase tables with an in-memory fallback for local dev. For production workshops, what's the data retention / cleanup story?**

- **Current default:** Data persists in Lakebase indefinitely; in-memory mode resets on restart (local only).
- **Open questions:** Do hackathons get archived/deleted after an event? Is there a per-workshop-instance data isolation concern (multiple cohorts sharing one deployment)?

**Q: Should the demo seed hackathon ship in production, or only locally?**

- **Current default:** A seeded "V2V Build-Off 2026" demo hackathon appears in in-memory (local) mode. Lakebase (prod) starts empty.

---

## 7. Surface & discoverability

**Q: Hackathons live as a separate destination (sidebar + bottom-of-front-page entry card), not woven into the 30-step journey. Is that the right placement?**

- **Current default:** Standalone destination. The workshop journey and hackathons are parallel, not sequential.
- **Open question:** Should completing the workshop *lead into* submitting to a hackathon (a capstone hand-off), or stay independent?

---

## 8. Dev experience & testing

**Q: We're adding a dev-only persona picker (switch acting user locally, like HackathonHive's UserSwitcher) and Playwright + pytest test suites. Any concerns about the dev-only auth override?**

- **Current default (proposed):** A persona switcher active *only* when `USE_LAKEBASE=false` / a `DEV_AUTH` flag — never in production. Enables local multi-persona testing + Playwright e2e.
- **Decision needed:** Confirm the gating approach is acceptable (it must be impossible to enable in a deployed app).
