# intent-beat-explain-complete

## Defect (verified at 4d93628, found by the #80 live probe)
On a fresh session (use case unresolved), vibe_next_step and vibe_get_step return the pre-journey intent beat `_INTENT_BEAT_STEP` (sectionTag `use_case_selection`, mcp_server.py:932; get at :1213, next at :1313). But:
- `vibe_explain_step(None)` (mcp_server.py:1350-1356) uses `engine.next_step`, which knows nothing of the beat, so it explains `project_setup`. That disagrees with get and next.
- `vibe_explain_step("use_case_selection")` goes through `engine.resolve_step` (:1358), which returns None for the beat (not a manifest step of genie-accelerator; the manifest only references it as a requiresGate, manifest.json:3335). Result: UNKNOWN_STEP.
- `vibe_complete_step("use_case_selection")`: the existing guards run first (:1606-1645: GATE_REQUIRED before confirmation, CUSTOM_DRAFT_REQUIRED for a custom lock without a draft; pinned by test_usecase_gate.py:86 and :178). Once those pass, `engine.complete_step` returns UNKNOWN_STEP. That covers both the confirmed-but-unlocked case and the already-locked case, the latter only if the confirm marker exists; otherwise the guard returns GATE_REQUIRED even after a successful lock. The design (comment at :925-931, test_usecase_gate.py:114, test_lock_produce.py:246) retired completing the beat through vibe_complete_step: `vibe_set_parameters` resolves the gate via `engine.resolve_use_case`. Agents still call it, because next and get hand them a step whose sectionTag is use_case_selection.
