# seed-new-rows-existing-install (D-37, revised after critic r1; critic r2 ACCEPT)

## Problem
In create mode (default since #109), scripts/setup-lakebase.sh's embedded Python (~:681-755) runs the bulk DML seed only when usecase_descriptions, section_input_prompts or step_visibility_overrides is EMPTY; otherwise it re-runs only 08/09 (POST_SEED_MIGRATIONS). So a NEW row added to 01_seed_usecase_descriptions.sql or 02_seed_section_input_prompts.sql (new explicit PK, e.g. P4.3 genie-code forks input_id 1001+) never reaches an existing install. D-14's premise ("the reseed delivers new rows") is false. This blocks P4.3.
Constraints (evidence @ca9ff61): 01 (48 INSERTs) and 02 (137 INSERTs, max input_id 958) carry explicit SERIAL PKs and NO ON CONFLICT; 01 has 3 unguarded UPDATEs (~:777/:1871/:1889) and no updated_by column; 03 is a .sql.template (not matched by get_dml_seed_files' *.sql glob, so this script never runs it); execute_sql_file is autocommit and swallows duplicate-key errors; the admin UI hard-DELETEs rows (routes.py ~:2710/:2752/:3344), so "insert any missing seed PK" would RESURRECT admin deletions; SERIAL PKs mean an admin-created row can occupy a future seed PK.

## Design
S1. New pure helper scripts/seed_new_rows.py (no DB driver import at module level; functions take a DB-API cursor):
  - split_statements(sql): a byte-for-byte MIRROR of setup-lakebase.sh parse_sql_statements (:391-475): single-quote strings with '' escapes, -- comments, paren depth, ';' at depth<=0, the no-semicolon salvage rule. NO dollar-quote handling (the runner has none; the seed files contain none, asserted by a test). A parity test runs both splitters (the shell's function extracted from the heredoc text) over 01 and 02 and asserts identical lists.
  - seed_rows(path, table, pk_col): the INSERT statements for that table with their explicit PK, parsed from the column list + first VALUES tuple; any INSERT whose PK can't be parsed is a hard error (fail closed, no write). UPDATE/DELETE statements are never returned.
  - apply_new_rows(cursor, schema, table, pk_col, rows, baseline, mode): see S3/S4.
  - raise_sequence_never_lower(cursor, schema, table, pk_col): computes the next value the sequence would hand out (last_value NULL -> start_value; is_called -> last_value+1; else last_value); calls setval(seq, max_pk + 1, false) ONLY if max_pk + 1 > next; otherwise no-op.
S2. Committed baseline scripts/seed_baseline.json: {usecase_descriptions: [config_id...], section_input_prompts: [input_id...]} = every PK present in 01/02 at ca9ff61. Baseline PKs are treated as ALREADY APPLIED on an existing install and are never (re)inserted by the helper. A test regenerates it from `git show ca9ff61:<file>` (fails, not skips, when git exists but the object is missing) and asserts equality.
S3. Additive DDL db/lakebase/ddl/14_seed_rows_applied.sql: CREATE TABLE IF NOT EXISTS ${schema}.seed_rows_applied (table_name VARCHAR(100) NOT NULL, pk INTEGER NOT NULL, applied_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, PRIMARY KEY (table_name, pk)). No ALTER/DROP.
S4. Populated-install path (create mode, table populated, after 08/09): for 01 and 02, for each seed row whose PK is NOT in the baseline and NOT in seed_rows_applied: INSERT ... ON CONFLICT (pk) DO NOTHING; if a row was inserted (rowcount 1) record (table, pk) in seed_rows_applied (ON CONFLICT DO NOTHING); if it conflicted with an existing row (rowcount 0) print a WARNING naming table+pk and do NOT record it (an admin row owns that PK; never overwritten, re-warned each run). Then raise_sequence_never_lower for both tables. Never runs 01's UPDATEs, never runs 03, never UPDATEs or DELETEs any row. Summary line: '<table>: N inserted / M warnings'.
S5. Fresh-install / bulk path: after the bulk seed and sequence reset in create mode AND in the --recreate branch, record EVERY post-baseline seed PK that now exists in its table into seed_rows_applied (INSERT ... ON CONFLICT DO NOTHING). Closes fresh install -> admin delete of a post-baseline row -> redeploy resurrection. Pre-baseline rows are covered by the baseline. --recreate doesn't drop the ledger; stale ledger rows are harmless because the recreate reseeds those rows.
S6. Per-table gating: the create-mode bulk gate also fired on a POPULATED install when only step_visibility_overrides was empty, re-running 01/02 in full (resurrecting admin-deleted baseline rows; running 01's 3 UPDATEs). Now: run 01 only if usecase_descriptions is empty, 02 only if section_input_prompts is empty, 08/09 always (ON CONFLICT DO NOTHING / updated_by='seed'-guarded). A populated table (COUNT>0, even partially seeded) takes S4; missing baseline rows are treated as admin deletions. One log line per table names the branch. Sequence reset after a create-mode bulk run uses raise_sequence_never_lower; the recreate branch's unconditional setval(max+1,false) (~:664-666) stays (tables just dropped).
S7. The helper is imported from the heredoc via a sys.path insert of PROJECT_ROOT/scripts; a helper failure prints an error and exits non-zero (the deploy stops; per-row autocommit inserts already made are each ledgered in the same step).

## Tests (offline, fake cursor; no DB, no network)
T-split parity (01, 02, adversarial strings with '' ; -- inside quotes); T-no-dollar; T-baseline equals ca9ff61 PKs; T-populated (baseline rows absent are NOT inserted; new post-baseline row inserted with ON CONFLICT DO NOTHING and ledgered; ledgered-then-deleted row NOT re-inserted; admin-held PK -> WARNING, not ledgered, no UPDATE); T-fresh (all post-baseline PKs ledgered after bulk; admin delete + rerun doesn't resurrect); T-recreate (stale ledger rows harmless); T-seq (NULL / is_called / not is_called; never lowers; raises when needed); T-gating (populated 01/02 + empty step_visibility_overrides -> no 01/02 statements, 08/09 run); T-noupdate (no UPDATE/DELETE/DROP/TRUNCATE emitted by the helper); T-unparseable PK -> hard error before any write.

## Live check (prober, after deploy with reseed=yes in DEFAULT create mode)
Before/after md5 of GET /api/all-data and GET /api/config/step-visibility-matrix identical; the tables-step log shows the per-table gating lines and '0 inserted / 0 warnings' for both tables; no sequence lowered.

## Decision D-37 (revised)
question: how do new seed rows reach an existing install? choice: baseline + ledger additive apply (S1-S7). evidence: setup-lakebase.sh:391-475, :640-755 @ca9ff61; routes.py hard deletes; critic r1 findings 1-3,5; critic r2 ACCEPT. reversal: git revert of this PR (restores the OR'd gate and drops the helper call); the ledger table stays (DROP is a human decision; destructive DDL is never done by the run).

## Design notes (lead resolutions, binding; added by the implementer)
(a) Parity: the test slices `def parse_sql_statements(` … up to `def execute_sql_file(` out of the setup-lakebase.sh heredoc text and exec()s ONLY that function definition in a fresh namespace; the script and the heredoc never run. A second test asserts the helper's split_statements source is byte-identical to that slice (name aside).
(b) Never-lower: the next value is read from the sequence relation (`SELECT last_value, is_called FROM <seq>`): last_value NULL -> start_value from pg_sequences; is_called -> last_value + 1; not is_called -> last_value. setval(seq, max_pk + 1, false) runs only if max_pk + 1 > next. The relation is read first on purpose: pg_sequences.last_value is also NULL whenever is_called is false (e.g. right after setval(seq, 2000, false)), so testing it first would report start_value and could LOWER a sequence an earlier setval raised. Tests cover NULL, is_called and not is_called, including the never-lower case (last_value 2000 not called, max 1001 -> no setval).
(c) Per-table gating: a table is populated if COUNT(*) > 0. A partially seeded populated table gets only the post-baseline new-row path; missing baseline rows are treated as admin deletions and are not restored. One log line per table names the branch (`<table>: empty -> bulk seed <file>` / `<table>: populated (N rows) -> post-baseline new-row apply …`).
(d) --recreate does not drop seed_rows_applied (its DROP list is usecase_descriptions + section_input_prompts only). After the recreate reseed, S5 ledgers every post-baseline PK present (ON CONFLICT DO NOTHING), so stale ledger rows are harmless: their rows exist again. Pinned by test_recreate_keeps_ledger_and_stale_rows_are_harmless.
(e) Correction to the Problem's "03 … this script never runs it": vibe2value generates the gitignored db/lakebase/dml_seed/03_seed_workshop_parameters.sql from the template (scripts/vibe2value.py:142, :1244; .gitignore:37), and the *.sql glob matches it. Before this change it ran in create mode whenever the OR'd gate fired, which included every fresh install. Running only 01/02/08/09 would leave workshop_parameters unseeded on a fresh install, so the create path runs seed files other than 01/02/08/09 (today only the generated 03) ONLY on a fresh install (every SEED_TABLES table empty), in the runner's sorted order. On a populated install they are skipped and logged (`<file>: existing install -> skipped`), so S4's "never runs 03" holds. --recreate is unchanged (it runs every seed file).
